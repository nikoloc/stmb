# Can Debugger

This is a project I used for debugging the CAN communcation on a board that caused
me troubles, but more importantly it was simultaneously used to test, develop
and improve the [fsra-build](https://github.com/nikoloc/fsra-build) build system,
hence it will also server as a base reference of how to use it in other projects.

## Project Structure

In order to use the build system you need to install it as a git submodule. The
process is explained in a greater detail in the `fsra-build` repository. Assuming
you followed the guide there, you should have `b` subdirectory in the root of the
project, as it is the case here.

In order to separate our code from the code generated by `CubeMX`, all of our
code is placed inside the `app` subdirectory. This is not a must, by it
makes the codebase more organized. The only bridge between the main program and
the app program is the call to `app()` in the `Core/Src/main.c` right after the
generated initialization code.

In order for the build system to pick up on our newly added files, `custom.mk`
is created and populated to add our include and source paths. As explained in
the `fsra-build` README, many other options exist here, like adding custom
scripts, targets, preprocessor defines etc. The scope of this demo project is
kept relatively small, hence only the needed include and source options are
extended. It would be a good idea to have a lot of the commonly used stuff
extracted into another `contrib/` directory in `fsra-build`, so everytime
you add something new to your project, you also put it in there, for future
reference to others. Example would be a target that generates the `.srec` files
for the bootloader, since that is a fairly common thing we do, and others will
find it useful.

Another integral part of the project is `project.sh`. Here, we define the project
attributes, like name, family of microcontrollers etc. This file needs to be sources
before any of the consequent actions, so the build system knows how to build, flash
the project and similar.

The last part are the required binaries the build system depends on. They are
listed in the `fsra-build` project repository, and need to be installed in order
for the specific scripts to work. For example, for the `b/build.sh` to work you
need `make` and `compiledb` installed and their names (or executable paths) set
in `FSRA_MAKE` and `FSRA_COMPILEDB` environment variables.

On Unix systems (Linux and MacOS) these can be obtained from the package repositories
and, since the names are usually standardized, it will probably suffice to just
call

```bash
source b/env.sh
```

For Windows, see notes in `fsra-build` and extend this guide after it has been tested.
